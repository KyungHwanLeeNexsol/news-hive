# SPEC-AI-071 Implementation Plan

## 설계 근거 (필터 위치와 기준)

**핵심 제약**: 탐지기 후보 유니버스는 `build_scan_universe`가 오직 `stocks` 테이블에서 구성한다
(SPEC-AI-065). 따라서 "어떤 종목이 `surge_candidate`가 될 수 있는가" = "그 종목이 `stocks`에
있는가" 다. 정답 수집기가 `stocks`에 없는 종목(레버리지/인버스 ETN·미추적 기업)을 정답으로
집계하면, 이들은 어떤 탐지기로도 잡히지 못하는 **영구 false negative**가 되어 recall/precision을
왜곡한다. 그러므로 정답 모집단을 `stocks` 존재 종목으로 교집합하는 것이 옳은 정제다.

**필터 위치**: 결합 `code_to_market` 집합(top-movers ∪ T-1-예측-보완) 구성 완료 직후(`:101` 이후),
가격 조회 루프(`:108`) 이전. 이 위치를 택하는 이유:
- 가격 조회 이전에 필터하면 제외 대상 코드에 대한 불필요한 `fetch_current_price_with_change`
  호출을 절약한다(레이트 리미트 완화).
- T-1 예측 보완(`:72-101`)이 이미 완료된 뒤이므로, 보완 종목(⊆ `stocks`)은 교집합에서 살아남는다
  — REQ-002 회귀 가드가 구조적으로 성립.

**필터 기준**: `db.query(Stock.stock_code).filter(Stock.stock_code.in_(<결합 코드>)).all()` →
존재 코드 집합. 결합 코드에서 이 집합에 없는 코드를 제거. 기존 종목명 보완 조회(`:152-157`)와
동일한 `Stock.stock_code.in_(...)` 패턴 재사용.

## 진입점 / 재사용 (신규 자산 최소화)

**재사용:**
- `collect_daily_surge_outcomes`(`surge_actual_outcome_service.py:40`) — 유일한 변경 대상 함수.
- `Stock` 모델 지연 임포트 + `Stock.stock_code.in_(...)` 조회 패턴(`:147-157`에 이미 존재).
- 기존 로깅 관례(`:103-106`, `:210-213`) — 제외 수 로그를 여기에 얹음.

**신규 자산:** 없음(신규 테이블·모델·마이그레이션·스케줄러 잡 없음). 순수 함수 내 필터 삽입.

## 마일스톤 (우선순위 기반)

1. **(PRESERVE) characterization test 작성** — 현행 `collect_daily_surge_outcomes` 동작 스냅샷:
   top-movers 전체 + T-1 보완이 upsert되고 `stocks` 부재 코드도 포함되며 `was_surge`가 그 부재
   코드까지 세던 현재 동작을 고정. (DDD 선행 단계, 코드 변경 전.)
2. **(P0) `stocks` 교집합 필터 삽입** — 결합 코드 집합 구성 직후 필터 삽입(REQ-001/003). 가격
   조회·upsert는 필터된 집합에 대해서만 수행.
3. **(P0) T-1 보완 회귀 가드 검증** — 보완 종목이 필터를 통과함을 characterization/단위 테스트로
   확정(REQ-002). `:72-101` 로직 자체는 무변경.
4. **(P1) 제외 수 관측 로깅** — 필터로 제외된 코드 수를 기존 로그 형식으로 남김(REQ-004).
5. **(IMPROVE 검증) characterization test 갱신** — 필터 적용 후 `stocks` 부재 코드가 upsert·
   `was_surge`에서 빠지는 신규 동작으로 스냅샷 갱신.

## 실패/엣지 처리 설계

- **`stocks` 조회 실패(SSL 끊김 등)**: 기존 종목명 조회(`:158-165`)가 실패 시 rollback+코드
  fallback으로 배치를 중단하지 않는 관례와 일관되게, 필터 조회 실패 시 **fail-open**(미필터 집합으로
  진행 + 경고 로그)한다. 근거: 일시적 DB 오류로 그날 정답 수집 전체를 잃는 것보다, 그 하루만 ETN
  집계가 재유입되는 편이 손실이 작다. rollback 필요 시 명시적으로 처리.
- **교집합 결과 0건**: 결합 코드가 전부 `stocks` 밖인 극단(정상 운영에서는 발생 어려움)에서는 upsert
  대상이 0 → 기존 "upsert할 레코드 없음"(`:142-144`) 경로가 그대로 처리(0 반환).
- **중복 코드**: `code_to_market`은 dict라 코드 유일성이 이미 보장됨 — 필터는 유일 집합에 적용.

## 롤아웃 전략 (전진 전용, 신호 생성 무변경)

본 SPEC은 정답 수집기 한 함수의 입력만 축소하므로 신호 생성/매수 로직 위험이 없다.

1. **백필 없이 전진(forward-only)** — 다음 `collect_daily_surge_outcomes` 실행부터 적용. 과거
   `SurgeActualOutcome`/`surge_prediction_evaluation` 행은 손대지 않는다(Exclusion 1).
2. **배포 확인** — 배포 후 첫 수집 로그에서 (a) 제외 종목 수 로그가 남는지, (b) `was_surge` 카운트가
   ETN 유입 이전보다 합리적으로 감소했는지, (c) T-1 예측 보완 종목이 여전히 포함되는지 확인.
3. **평가 지표 재해석 유의** — 필터 적용 시점 전후로 recall/precision 분모가 달라지므로, 시계열
   비교 시 배포일을 경계로 인지(단, 과거 재계산은 하지 않음).
4. **Deploy Guard** — 15:15~16:10 KST 자동 대기 창 준수(기존 배포 파이프라인 관례).

## 리스크

- **정상 종목의 과도 제외 위험** — `stocks` 커버리지가 실제로 부족해 정상 급등주가 미추적 상태면
  필터가 그 종목까지 제외한다. 그러나 그런 종목은 애초에 `surge_candidate`가 될 수 없으므로 정답에
  남겨도 구조적 FN일 뿐 — 근본 해법은 유니버스 커버리지 확장(별도 SPEC-AI-065 계열)이지 정답 오염이
  아니다. REQ-004 로깅이 제외 규모를 관측해 커버리지 문제를 조기 신호한다.
- **fail-open 시 일시적 ETN 재유입** — `stocks` 조회가 실패한 날은 미필터로 진행되어 ETN이 하루
  집계될 수 있음. 배치 무손실을 우선한 의도적 트레이드오프(경고 로그로 표면화).
- **평가 시계열 단절** — 배포 경계에서 분모 정의가 바뀌어 recall/precision 추세가 계단식으로 변할 수
  있음 → 과거 재계산 대신 배포일 경계 인지로 대응.
